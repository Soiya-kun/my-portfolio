01ミッション・価値観への共感

困りごとを見過ごせない。その性質を、行政・政治の改善にも活かしたい

私は、自分の本質として、自身が遭遇した困りごとを見過ごせない性質があると思っています。正社員として働くDigeonでも、副業で支援する精和工業所でも、それが仕事を引き受け、改善に関わり続ける出発点になってきました。

二つの現場で、自分が手を動かす

Digeonに参画した当初は、人手が足りず、日々の案件を進めるだけでも手いっぱいの状況でした。プロジェクトの進め方も体系化しきれておらず、目の前の開発を担いながら、案件を継続して進められる仕組みを整える必要がありました。私は、その状況を見過ごせず、PMとリードエンジニアの両方を担い、開発とプロジェクト運営の標準化に取り組んできました。

精和工業所では、システムやソフトウェアに詳しい人が少なく、業務で使うソフトウェアの改善を進める担い手がいない状況がありました。負担が残っているのに、改善に手をつけられない。その状況も気になり、副業として支援を続けてきました。

こうした困りごとに対し、私はそこで手を動かすことによってコミットメントを続けてきました。必要な仕事を引き受け、相手と話し合いながら、プロジェクトの進め方を整え、業務を支えるソフトウェアを実装する。二つの現場で、そのとき必要な改善を自ら形にしてきました。

手を動かし、相手の事情から考える

精和工業所では、既存の基幹システムで扱えない工程管理を、RPAを使って自ら実装しました。一方で、利用者が自立して開発するという導入の狙いは、十分には実現できませんでした。適性や時間の制約もあり、ツールを渡せば誰もが使いこなせるとは限らないと学びました。

AIを日常的に使っている私自身ですら、AIと会話する方式には馴染めない感覚があります。だから、使わない人の姿勢だけに原因を求めず、何が妨げになっているのかを理解したい。相手を責めるより、一緒に使える方法を探したいと考えています。「誰かをおとしめない」「分断を煽らない」という価値観を、日々の仕事でもこうした姿勢として実践していきたいです。

情報を開き、自分の進め方も見直す

PMとしては、自分が慣れた進め方で合意形成に失敗した経験があります。その後は、相手方PMと事前に進め方を合わせ、確認対象、未決事項、予定と実績を共有する方法へ改めました。関係者が同じ情報を見て、次の判断をできる状態をつくることを重視しています。

自分のやり方を正解と決めつけず、実際に起きたことから学び直す。判断の前提を共有し、相手と進め方をつくる。「オープンにする」「何事も決めつけない」という価値観は、この経験と重なります。

これまでの取り組みを、行政・政治の改善へ

正社員と副業のそれぞれで、自分が担ってきたミッションを達成できつつあると感じています。その中で、これまでの経験を活かして新たな道に進みたいという気持ちが芽生えました。もともと関心のあった行政・公共の領域で、困りごとを見つけ、自ら手を動かす姿勢を活かして働きたいと考えています。

チームみらいが掲げる、テクノロジーによって政治を透明にし、人々が参加しやすくするという方向性を、私は、現場の改善を積み重ねて社会の仕組みを変えていく取り組みだと受け止めています。困りごとに気づいたところから、自分の手で改善を始める。その姿勢に、自分の仕事との接点を感じています。

募集をXで見たとき、すぐに応募に向けて動き始めたのは、自分が気にし続けてきたことと、チームみらいの価値観がつながると感じたからです。PMとリードエンジニアとして培った、相手と合意をつくり、自ら実装して改善を進める力で貢献したいと考えています。

02オープン・コミュニケーション

情報を共有し、関係者が判断できる状態にする

PMとリードエンジニアを兼ねる中で培ってきたのは、技術面の責任を担いながら、顧客と開発チームが同じ状況を見て判断できる土台をつくる力です。合意事項、未決事項、予定と実績のずれを整理し、何が終わり、何が残り、どこに相談が必要なのかを共有します。この情報共有・管理のスキルを、オープン・コミュニケーションに生かしたいと考えています。

合意形成の失敗から、進め方そのものを合意するようになった

数百万円から億単位まで、大小さまざまなプロジェクトを経験し、規模を問わず、一貫して顧客との合意形成とプロジェクトマネジメントを担ってきました。自ら開発する比重は案件によって変わりますが、関係者と認識をそろえ、プロジェクトを前に進める役割は変わりません。

それまでは、アジャイル的に動きながら具体化する進め方を多く採っていました。しかし、ウォーターフォール型の契約を前提とする案件では、顧客が判断・合意するための説明や筋道を十分に整えられず、合意形成に失敗しました。

この経験から、次の案件では、キックオフ後に何をどのように進めるかを、相手方PMと事前に合意するプレキックオフを重視するようになりました。その具体的な方法が、AsIsの全量管理と、アプローチ図を使った運営です。

確認対象を合意し、実測から計画をつくる

要件定義の初期には、現行業務の詳細をまだ把握できていません。それでも、何をヒアリングする必要があるか、そのタイトルの全量は顧客と早い段階で合わせることができます。

プレキックオフでは、その全量と、確認セッションを組めるペースを相手方PMと合意します。実際のヒアリングで1項目のボリュームを測り、その実測を計画に反映していきます。

  1. 対象を揃える。 ヒアリングすべきタイトルを一覧にし、確認する範囲を顧客と合意する。
  2. ボリュームを測る。 セッションを実施し、1項目にかかる時間や確認量を把握する。
  3. 先を予測する。 残項目のボリュームとセッションを組めるペースから、今後の進捗を見積もり、計画と優先順位を組み立てる。

これによって、時間が足りない、日程を組めない、確認項目が増えた、といった変化を、合意した対象・ペースとの差分として扱えるようにします。

計画と実績を、アプローチ図で共有する

計画を立てた後は、その全体像を共有し続ける必要があります。そこで、AsIsの確認、ToBeの検討、議論、合意といった大きな作業を、看板のように一覧できるアプローチ図にします。

図には完了・予定・必達期限を追記し、定例で前週からの変化を確認します。経過した時間に対してどれだけ作業が残っているかを、顧客と開発側が同じ図で確かめるためです。遅れや未決事項があれば、その場で次の動きや必要な判断を話し合います。

アプローチ図の例と、定例での運用を見る

説明用の架空例です。実案件の進捗・日程を示すものではありません。

全体の道筋を、作業と状態で共有する

AsIsの確認からToBeの合意までを、大きな作業単位で並べます。各作業に状態と予定を付け、今どこにいるか、次に何をするかを示します。

  1. 完了01　AsIsを明らかにする

    ヒアリングタイトルの全量を合意し、現行業務を確認する。

    例：確認完了。追加論点は別途記録。
  2. 進行中02　ToBeを検討する

    現行の課題と、変更後の業務案を整理する。

    例：今週、案を整理。未決事項を明示。
  3. 予定03　ToBeの議論会議

    案と論点を共有し、関係者と選択肢を議論する。

    例：来週開催予定。事前に案を共有。
  4. 合意期限を管理04　ToBeに合意する

    決めた内容と残る事項を確認し、合意を記録する。

    例：議論後に判断。期限は顧客と設定。

論点が残ればToBeの検討へ戻ります。順番だけでなく、戻る理由も図に追記します。

定例での使い方

  1. 前週からの変化を追記する。 完了した作業、現在の実績、予定日、必達期限を図に反映する。
  2. 計画との差分を一緒に確認する。 経過した時間に対して何が残っているか、予定どおり進んでいない箇所はどこかを確認する。
  3. 次の動きと必要な判断を決める。 残作業や未決事項について話し合い、次回までに行うことを更新する。

AsIs全量管理から、図の予定を組み立てる

タイトルの全量を合意 → 1項目のボリュームを実測 → 残量とセッションのペースから進捗予測 → 計画・優先順位を設定

全量管理は予定を立てる根拠、アプローチ図は全体の道筋と実績を共有するために使います。確認が長引く、項目が増える、セッションを組めないといった差分は、計画と図の両方に反映して運用します。

未知があることも、管理の前提にする

この方法では、まだ把握できていないことが後から明らかになる可能性も織り込みます。まず双方が決められる範囲を出し切り、確認対象・セッション計画・アプローチ図という管理可能な形にする。そのうえで、実測や新たな発見に応じて更新していきます。

合意形成での失敗を経て、私は、進め方を事前に合わせ、進行中も同じ情報を見て調整するところまでを、PMの仕事として組み立てるようになりました。

経験の浅いPMも、根拠を持って交渉できるようになった

私の経験では、AIで実装を進めやすくなった今も、認識のずれや調整の難しさが表れやすいのは要件定義です。AsIsの全量とアプローチ図を運用することで、この時期に何が決まり、何が残り、どこに調整が必要かを見通しよく共有できるようになりました。

特に大きかったのは、経験の浅いPMでも、相手の要求をそのまま受け入れてしまう場面が見られなくなったことです。会話の材料が整理されていれば、要求が既存の合意や計画にどう影響するかを示し、何を調整すべきかを話し合えます。個人の交渉経験に頼る部分を減らし、共有した情報を根拠に対話できる状態をつくりました。

03オーナーシップ

チームの隙間に残る仕事を、自分が引き受ける

複数案件をまたぐ場面では、各プロジェクトのボトルネックを見て、適性のあるメンバーを配置し、最後に残る仕事を自分が引き受けてきました。マネジメントから設計・開発まで担当できる幅を生かし、自分の役割を固定せず、チーム全体で仕事を完了できる分担をつくる。この進め方で、Digeonの創業期を支えてきました。

接続権限と人員配置を踏まえ、インフラ構築も引き受ける

外部エンジニアと開発する案件では、顧客インフラへの接続を原則として正社員に限定していました。他の正社員が別案件を担当している場合には、私がインフラの設計・構築を引き受けることが多くありました。

人員の適性だけでなく、アクセスできる範囲も踏まえて役割を組み、開発に必要な仕事を自ら担ってきました。担当者の途中離脱により残ったコアロジックとインフラを引き継ぎ、納品まで進めた経験もあります。

04学習意欲

責任を持って対処する問題は、誰よりも深く理解できるように学ぶ

自分が責任を持って対処しなければならない問題に対して、理解の解像度を高めるためにキャッチアップを続けられることが、私の強みです。特に、自分が判断し、解決まで担う必要がある場面では、誰よりもその問題と関連技術に明るくありたいという姿勢で学んできました。

PMとして、システムの設計と納品にも責任を持つ

これまで、PMとしてプロジェクトを進めると同時に、リードエンジニアとしてシステムの設計にも責任を負ってきました。納品するシステムに責任を持つ以上、技術的な判断の根拠や、問題が起きる仕組みを自分自身で理解する必要があります。その責任を果たすために、案件で必要となる技術を学び、設計や実装に結びつけることを続けてきました。

動画解析アプリケーションの開発で、不具合の残るコアロジックとインフラを引き継いだ際も、当時は得意分野ではなかったアルゴリズムやインフラについて、AIを活用しながらキャッチアップし、納品まで進めました。必要な知識が足りないときに、自分の理解を深め、実際の問題に対処するところまで取り組む姿勢は、この経験にも表れています。

新しい領域でも、具体的な問題から理解を深める

日頃も、趣味で開発しているアプリのアーキテクチャやBeyondCorpの導入設計など、具体的な課題を題材に、AIとの壁打ちを通じて理解を深めています。実際にどう設計するかを考えることが、学びを深めるきっかけになっています。

政治・政策の知識は、これから深めていく段階です。答弁や討論番組、チームみらいの動画などを通じて論点に触れながら学んでいます。この領域でも、自分が担う問題に責任を持ち、判断と行動に必要な理解を深め続けたいと考えています。

05柔軟性

プロジェクトの成功を第一に、水のようにチームの隙間を埋める

私のオーナーシップの根本には、プロジェクトの成功そのものを常に第一に考える気質があります。その姿勢が、そのまま私の柔軟性につながっています。

さまざまな背景や強みを持つメンバーと仕事をする中で、チームの能力のバランスは案件ごとに大きく変わってきました。成功に必要な力が足りなければ、その不足を残したままにはできません。一方で、一人ひとりに得意なことや適性があり、役割を変えるだけですべてを補えるわけでもありません。

自分が水になり、そのとき最も価値のある役割を担う

そこで、自分が水になるのだと考えています。岩、石、砂が詰められた箱に注ぐ水のように、メンバーの強みを活かしたうえで残る隙間を、自分が形を変えて埋める。その瞬間にチームが必要としている役割を担うことが、自分にできる最大の付加価値だと思っています。

自分が最も価値を発揮できる役割を担うことには、自然と喜びを感じます。それがプロジェクトの成功につながると信じているからこそ、PM、設計、実装のどこに力を注ぐかを変えられる。この性質そのものが、私の柔軟性です。

メンバーの強みを活かし、残る実装を引き受ける

PMと開発のどちらに比重を置くかは、チームの構成に応じて変えています。外部エンジニアと進めた案件では、開発が進む中で、使用言語への習熟度を踏まえた役割の調整が必要になりました。

その方は自社開発のデータ分析プロダクトの出身で、腰を据えて設計し、じっくり開発を進める仕事に向いていました。そこで、コアロジックの設計とSQLを中心とする開発を担当してもらいました。一方、マスタ管理など、実装方針が決まっている基本機能は、その方に新たな学習コストをかけてもらうより、慣れている私が素早く実装する方が適切だと判断しました。

私はマスタ管理基盤やUI/UX全般を担い、この分担で完成させました。既に持っている強みを生かせる仕事と、習熟によって速く進められる仕事を分け、チーム全体として完成までの道筋を組み立てています。

10仮説検証の経験

相談から1週間で実装し、再ヒアリングで発注データ入力までなくす

出発点は、備品発注フォームを作りたいという具体的な相談でした。私は、今後ほかの業務でも入力と承認の仕組みが必要になると見込み、共通利用できるフリーフォーム機能として設計・実装しました。相談から実装までは1週間でした。

まず、データ入力と承認フローを共通化

入力と承認を抽象化した機能を使って、紙で回していた備品発注をフォームに置き換えました。当初の要望を満たし、利用者からは喜びの声をいただきました。そのうえで、導入後の仕事が実際にどのような順序になったかを再ヒアリングしました。

備品発注で分かった、フォームの外側の仕事

再ヒアリングで分かったのは、発注対象が基幹システムのマスタで管理されていることと、承認後の発注情報を基幹システムへ手入力する作業が残っていることでした。フォームの導入後も、その外側には改善できる仕事がありました。

そこで、前後の作業も含めた改善を再提案し、備品発注固有のフォームとして実装しました。結果として、基幹システムへの発注データの手入力もなくしました。まず1週間で相談に応える仕組みを作り、利用後の仕事を聞き直して、次の改善につなげる。この2段階で、現場に合わせて最適化しました。

この取り組みは、i-Reporterに代わる業務アプリの開発・導入の一部です。i-Reporterを一定の利用水準まで引き上げた経験はあったものの、全体としては失敗だったと捉えています。その後、副業で業務アプリの開発を支援し、全面的な置き換えへ進みました。

13生成AIを活用した開発の実務経験・関心

AIが実装する時代に、設計者が読むべきコードを明確にする

PoCから実装まで、AIを開発の実務に組み込む

3案件を並行していた時期には、Figma Makeでモックを作り、CodexのWeb版と組み合わせて実現可能性を検証しました。自ら設計した内容を実装へつなぎ、増員が難しい状況で開発を進めました。未知の技術領域を引き継いだ別案件では、o3を活用して納品まで進めています。

この時期の5月から翌年1月にかけて、自分一人で月あたり約300件、期間全体では3,000件を超えるPRを作成しました。いずれも当時の概数です。

AIの能力を実際に試して開発方法を変える一方、重要な設計と実装の意味を確認する責任は、自分が担うと考えています。

AIの進化に合わせて、確認方法も変えてきた

AIへの任せ方を広げる中で、確認方法も段階的に変えてきました。コードを読む範囲、設計の詳しさ、自動テスト、別のAIによるレビューと操作確認を組み合わせています。

初期：難しいReactコンポーネントを、全コードレビューで確かめる

実装難度の高いReactコンポーネントをAIに実装させ、生成されたコードをすべて読み、妥当性を自分で評価しました。

中期：厳密な設計とレビューに、DBを通した自動テストを加える

設計を人が厳密に行い、AIのコーディング結果も厳密にレビューしました。さらに、DBまで通して確認する自動テストを導入し、コードの読み取りに加えて動作を検証するようにしました。

後期：重要なコードに読む範囲を絞り、別のAIでも確認する

設計の記述を簡略化する一方、重要なコードの可読性を保つCIを設け、人が読む範囲を絞りました。また、実装時のコンテキストを減らした別のAIにレビューや動作確認を任せるようにしました。

現在：実装の経緯を渡さず、業務シナリオから操作させる

現在は、実装時のコンテキストを渡していないAstraに、業務上のシナリオを伝えてシステムを操作させています。網羅性と厳密性に注意するよう指示し、その動作確認の様子を自分で見続けます。AIが明らかに迷ったところでは、必要な情報だけを補います。

業務シナリオによる操作確認に加え、DBまで通す自動テストと、重要なdomain・interactorのコード確認は現在も継続しています。AIへの任せ方が変わっても、これらを併用して品質を確認しています。

自動テストをいつ作成し、いつ実行するかについては、現在も運用を検討しています。以下の設計規則とCIは、こうした検証と並行して、人が重要なコードを読み続けるための土台です。

業務の意味と実装が一致するかは、人が見届ける

生成AIでコードを書くことが容易になっても、重要な機能の設計と、その意図が実装に表れているかの確認は、人が担う必要があると考えています。日本語で説明した業務ルールが、実際にはどの条件や処理になっているのか。設計者として、その対応を自分で読むべきコードが必ずあります。

その確認をしやすくするために、私はGoのクリーンアーキテクチャとDDDを土台として、業務知識の置き場所と書き方を厳密に定めました。目指したのは、コードを業務のドキュメントとしても読める状態です。

domainで判断を、interactorで手順を読む

実際の振る舞いの正となるコード（SSoT：Single Source of Truth）から業務を理解するために、domain層へ知識・制約・判断を集め、interactor層にはユースケースの手順を記述する方針にしています。

interactorで処理の順序と呼び出す業務判断を追い、その判断の中身はdomainで確認する。外部I/Oや入力変換の細部に埋もれず、業務の意味をこの2層を中心に読み取れるようにするための規則です。

読み方を保つため、書き方をCIで検査する

この構造を継続して保つため、命名、分岐、入力境界、呼び出し方まで規則にし、固有のCIへ落とし込みました。

  • 業務判断をdomainに集める。 知識を表す純粋関数と、可否・整合性を判定するpolicyを配置。外部I/Oを分離し、時刻などの環境依存値は引数で渡す。
  • interactorでは、意味のある手順を読む。 業務分岐は名前付きのDecisionを介し、汎用的な動詞を避けて業務目的が分かる名前を付ける。値を返す呼び出しは意味の分かる変数で受け、使用箇所の近くに置く。
  • 入力の解釈と制約をdomainの境界に閉じ込める。 interactorでのJSON復元・時刻の解釈・Value Objectの直接生成を制限し、用途の分かるdomain関数に集約する。
  • 規則を自動検査につなげる。 interactorの構造・呼び出し・domain境界・可読性、repositoryの入力境界などをCIで検査。可読性の既存違反は記録し、新規・増加を検出しながら段階的に減らす仕組みを設ける。

CI・コードリーディング・動作確認を組み合わせる

CIで規則への適合を検査し、設計者はdomainとinteractorを読んで業務上の意味を確認する。さらに動作確認で、実際の振る舞いを確かめます。それぞれが何を確認するかを明確にし、AIを使った実装でも設計意図との対応を追えるようにしています。

コードとCIで、何を確認するか（掲載案）

複雑な更新処理の中から、対象・更新条件・編集可否を確認する部分を選びました。以下は実装をもとに名称を一般化し、周辺処理を省略した説明用の抜粋です。単独で動くコードではありません。

interactor：業務上の確認を、手順として読む

// 更新処理の一部：業務固有の名称を一般化し、前後の処理を省略
if policyErr := record.EnsureTargetKind(current); policyErr != nil {
    return nil, policyErr
}
if policyErr := recordupdate.EnsureExpectedVersion(current, selector); policyErr != nil {
    return nil, policyErr
}
if policyErr := record.EnsureVersionEditable(current); policyErr != nil {
    return nil, policyErr
}

何を確認してから更新するのかを、呼び出し順で追います。個々の判定の詳細はdomainを読みます。

domain：日本語のルールと照合する

「未提出の状態だけ編集できる」という業務ルールなら、その条件が実装にも表れているかを設計者が確認します。

// domain：名称を一般化した掲載用の抜粋
func EnsureVersionEditable(header RecordHeader) error {
    if header.Status.Value() != recordvalue.StatusUnsubmitted {
        return ErrNotEditable
    }
    return nil
}

CI：この読み方を保つために検査する

  • check-interactor-calls：呼び出し直後のエラー処理や、分岐の深さなどを検査。
  • check-interactor-domain-boundaries：入力解釈やValue Object生成がinteractorに散らばることを制限。
  • check-interactor-readability：命名、業務分岐、呼び出し結果の変数化・使用箇所への近接などを検査。
  • check-repository-boundaries：永続化へ渡すdomainの入力境界を検査。

CIで規則への適合を確認し、人は業務ルール自体が正しいかを読み、動作確認で実際の振る舞いを確かめます。可読性には既存違反を記録して新規・増加を検出する仕組みがあり、段階的に改善しています。

私が最適化したいのは、重要なコードを人が読み、判断する過程です。読む場所と読み方を揃え、その構造をCIで保つことで、設計者が業務の意味を確かめることに集中できる状態を目指しています。

設計の背景は、2026年2月に公開したGo・DDD・クリーンアーキテクチャについての記事でも説明しています。当時のAI（GPT-5.2）で執筆した記事のため、読みにくい箇所がある点にご留意ください。現在は、入力境界やinteractorの可読性をさらに細かな規則とCIに落とし込んでいます。
