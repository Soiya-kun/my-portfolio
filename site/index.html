伊藤 誠也 PM・リードエンジニア

顧客との合意から、
業務システムの設計・実装まで

株式会社Digeonで、受託開発のPMとリードエンジニアを兼ねています。顧客と要件や進め方を決め、業務上のルールをコードに落とし込み、実装とテストまで担当します。

PM経験約300万円〜約2億円規模の受託開発 アーキテクチャ業務ルールを読めるコードと要件を検証するテスト 案件履歴基幹システム・SaaS・業務Webアプリ

プロジェクトマネジメント

約300万円規模の受託案件では、顧客折衝から開発まで一人で完了しました。約2億円規模の案件では、PMとして設計の中核と技術面の責任を担いながら、顧客との合意形成に重心を置きました。チームは案件により2〜8名で、設計や実装の分担を組み替えながら進めてきました。

キックオフ前に、要件定義の進め方を合意する

ウォーターフォール型の契約を前提とした案件で、要件を動きながら詰める進め方を取り、顧客の判断に必要な説明や合意の順序を十分に整えられませんでした。その経験を受け、次の案件からキックオフ前に相手方PMと要件定義の進め方を決めるようにしました。

  1. 確認対象と進めるペースを合意する。 現行業務（AsIs）で確認すべき項目を一覧にし、顧客とセッションを組める頻度を決めます。
  2. 実測をもとに計画する。 初回のヒアリングで1項目の所要時間と確認量を把握し、残りの項目とセッションの頻度から進捗を見積もります。確認項目の追加や日程のずれは、合意した計画との差分として扱います。
  3. 顧客との定例で計画を更新する。 現行業務の確認から新業務（ToBe）の合意までを図にし、完了・予定・合意期限を共有します。前週からの変化を見ながら、残作業や判断が必要な論点を整理します。

これらの手順を社内で使える形に整理しました。経験の浅いPMも、新しい要望が既に合意した範囲や日程にどう影響するかを示し、顧客と調整できるようになりました。

増員が難しい案件で、顧客への提案をPoCで検証する

運送系の基幹システムを含む3案件を並行していた時期に、顧客が求める配車画面を既存の体制で実現できるかが課題になりました。そこで、運転手・車両・積荷注文をドラッグ＆ドロップで割り当てるモックをFigma Makeで作り、Codexを使ってAPI連携まで試しました。

数時間のPoCで実装の見通しを立て、操作できるモックを顧客に提示して認識を合わせました。そのまま設計と実装を進め、本番リリースまで担当しました。

ソフトウェアアーキテクチャ

業務上の判断をコードのどこで読めるか、要件の変更をどのテストで確かめられるかを設計します。Goの受託案件では業務ルールと処理手順を整理し、TypeScriptの公開実装ではその考え方を要件定義や画面テストに広げています。

業務フローをテストとして実行する

React・Honoで、売上登録から請求の締め・発行、入金管理までを扱う業務Webアプリの土台を作りました。例えば「月次の請求」の業務フローから「入金を記録する」シナリオを開き、その画面操作と、対応するバックエンド処理・SQLまでたどれます。

  • 要件とテストをつなぐ。 業務フロー、担当者、画面操作をTypeScriptで記述し、同じ業務フローをブラウザのE2Eテストとして実行します。個別シナリオの結合テストでは、画面から業務処理までを同一プロセスで動かし、DBを差し替えます。
  • 業務の言葉を揃える。 共通の単語帳から画面の文言を生成し、コードの命名も検査します。静的解析で処理を日本語に変換し、業務フローから実装をたどるブラウザ表示に使います。
  • 合意の経緯を追えるようにする。 議事録の決定事項・課題や、現行業務から新業務への置き換えを、業務フローや画面・処理の定義に関連付けます。

GitHubで実装を見るZennで「TypeSafe要件定義」を読む

Goで業務ルールと処理手順の置き場を決める

Goの業務システムでは、クリーンアーキテクチャを土台に、DDDのValue Objectやポリシーを取り入れました。状態や入力の制約・更新可否は domain、処理の順序と外部I/Oの調整は interactor、DBへの読み書きは repository で扱います。例えば「未提出のデータだけ編集できる」というルールは domain に置き、interactor を読めば更新の前にどの条件を確かめるかが分かります。

入力境界や呼び出し方、命名などはCIで検査します。AIを使って実装した場合も、設計者が業務上の判断を読む箇所を絞り、DBまで通す自動テストと業務シナリオに沿った操作で振る舞いを確認します。

業務判断をコードとCIで確認する例

以下は業務固有の名称を一般化した抜粋です。interactor では、対象・バージョン・編集可否を確認する順序が読めます。

if err := record.EnsureTargetKind(current); err != nil {
    return nil, err
}
if err := recordupdate.EnsureExpectedVersion(current, selector); err != nil {
    return nil, err
}
if err := record.EnsureVersionEditable(current); err != nil {
    return nil, err
}

domain では、編集可否の具体的な条件を確認できます。

func EnsureVersionEditable(header RecordHeader) error {
    if header.Status.Value() != recordvalue.StatusUnsubmitted {
        return ErrNotEditable
    }
    return nil
}

CIでは、呼び出し直後のエラー処理や入力解釈の位置、業務分岐の書き方を検査します。既存の可読性違反は基準値を記録し、新規追加や件数の増加を検出します。
